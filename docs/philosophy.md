# ソフトウェアガーデンの思想

ソフトウェアの原点は、人の「こうあってほしい」という欲求にある。誰のどんな願いをかなえたいのか。何ができるようになり、どんなことが起きてはいけないのか。それを考え、仕様として定めることに、人が最も力を注ぐ。

## ソフトウェアが育つ環境をつくる

ソフトウェアを植物として考える。植物を育てるには、その種類や育つ場所に合った環境を整え、いつ手を入れ、何を見て収穫の時期を知るかという知識が要る。

このリポジトリ（ナーサリー）は、そうした育て方の知識を、繰り返し使えるテンプレートとして持つ。対象リポジトリに、ソフトウェアの種類に合う手順や道具、設計上の制約を組み合わせる。これがエージェントの作業と検証を支えるハーネスになる。そこに製品固有の仕様と検証方法を与えることで、そのソフトウェアのガーデンが生まれる。

## 人の仕様を起点に、実装と検証を委ねる

ガーデンでは、作業の依頼や変更の到着といった出来事をきっかけに、AIが人から任された範囲で実装と検証を繰り返す。実装の途中で「どうあるべきか」が仕様から決まらないときは、人に問いを返す。

AIが実装とテストの両方を作れば、どちらにも同じ思い違いが入りうる。検証は人が仕様に定めた受け入れ条件から組み立て、実際の振る舞いと照らし合わせる。常に守るべき性質は不変条件として明示し、必要に応じてモデル検査や定理証明などの形式検証を使う。その結果には、どの性質を、どんな前提のもとで確かめたかを残す。

## ガーデンが結実を知らせ、人が収穫を決める

育成の途中では、あらかじめ人が任せた範囲で、検証を通った変更を自動で取り込める。ソフトウェアが仕様を満たしたとガーデンが判断したら、成果物に検証結果を添えて、結実（収穫の準備ができたこと）を人に知らせる。

最後に「欲しかったものができた」と判断し、最終的にリリースできる状態（収穫）と認めて出荷を決めるのは人である。期待に届かなかったとき、仕様に定めた挙動が欠けていれば、ガーデンは実装と検証に戻る。成果物を手にして初めて言葉になった期待は、人が次の仕様に書き込む。

## 育てた経験を、次のガーデンに生かす

人が毎回同じ点を確かめ、同じ理由で手直ししているなら、その判断を次の育成に生かせる。まずそのガーデンの設計や検証を改め、次に同じ問題が起きたときに防いだり検出したりできることを確かめる。他のガーデンでも役立つ知見は、それが有効な条件とともに、ナーサリーのテンプレートに還元する。

一つのガーデンでソフトウェアが育ち、その経験によって、次のソフトウェアを育てる環境もよくなっていく。これが、ソフトウェアガーデンで実現したいソフトウェアファクトリーである。
