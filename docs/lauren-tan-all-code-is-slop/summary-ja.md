# All Code Is Slop (Except Mine) — 要約

- 講演者: Lauren Tan (poteto)、Principal Engineer, SpaceXSI（Grok Bot）
- AI Engineer CODE 2026、2026-11-11、約17分
- 出典: AI Engineer 公式トランスクリプト https://ai.engineer/code/2026/talks/lauren-tan
- 動画: https://www.youtube.com/watch?v=O_zcc6Xl12g

## 結論
エージェントに大量のPRを出させる鍵は「工場」ではなく「信頼」。信頼は AGENTS.md の文章ではなく、エージェントの環境（コードベース・静的解析・検証）への投資で作る。内側のループが slop を出すなら、自動化は slop を速く大量に生むだけ。

## 信頼ピラミッド（逆ピラミッド）
下ほど厚く投資する。
1. コードベース自体（API設計、アーキテクチャ、リファクタリング）— 決定的
2. lint・型・コンパイラ・テスト — 決定的
3. 検証（ランタイム検証＋形式検証）
4. 文章のルール（rules、skills、AGENTS.md）— 薄く

## コードベースは庭
- コードは「数本のPR」から「連続した流れ」に変わった（2024年: 同僚のPR 3本レビュー → 今: 約300本）。エンジニア1人＝エージェント数百〜数千のチーム。
- コードベースはエージェントへの最大の入力。アンチパターンや回避策は「次のエージェントが既存パターンとしてコピーする」＝雑草が広がる。だからコードベースを pristine に保つ。エンジニアの仕事はガーデニングに近づいている。
- エージェントを直すときは、AGENTS.md に1行足すのではなく、決定的なチェック（コード）に変える。再現性が高く、信頼できる。

## Dune（Grok Bot のクライアントフレームワーク）の実例
- 「ニュアンスが要るものは slop を生む」: React の useEffect はプロダクトコードで禁止（Dune の API 内部のみ許可）。この種のレビュー指摘が消滅した。
- ディレクトリ構造で文脈を与える: electron-main / electron-renderer をトップレベルに分け、相互 import を依存グラフ解析＋lint で禁止（Cursor でエージェントが main を renderer に import して jank を起こした教訓）。
- コメントは抜け道になる: Cursor では setTimeout 等のタイマーがアーキテクチャの衝突への安易な修正として広がり、コメントがその正当化に使われ、GC のラグを招いた。Grok Bot ではコメントの99%を禁止（古くなる、読まれない、強制力がない）。代わりに「根本原因を直せ」と案内する親切なエラーメッセージ付き lint を置く。
- 直すたびにチェック化／問題のカテゴリ自体を設計で消す、を繰り返すとレビューで見るものが減り、やがてエージェントが自分のPRの大半を自分でマージできるようになる。

## 検証（verification）
- コードレビューは「検証の成果物（動画・スクリーンショット・図・形式検証）を見る」形に縮んだ。
- ランタイム検証: エージェント自身が Chrome DevTools Protocol 等の人間用ツールでコードを動かす。feature map（ユーザー視点の全機能のサイトマップ）で共通語彙を持たせ、スキル内のカスタム CLI を再利用（トークン節約＋テスト可能）。
- 形式検証: TLA+ で主要ユーザーフロー（複数デバイス/プラットフォームの通知）をモデル検査、自作仮想化ライブラリは Lean で証明（ちらつき等の不在）。実際にバグが見つかった。銀の弾丸ではなく、もう1つの層。
- UI のプロパティベーステスト: Bombadil。UI バグを検出。
- 他者の例: 6か月前は「微妙なバグがマージされる」ためエージェントを信頼できなかった人が、今は1日のトークンの70%を検証に使っている。Tan 自身もトークン使用の大半は検証。
- 手法自体は目新しくない。以前は高コストで手が出なかった良いプラクティスを、エージェントが安くした。「ソフトウェアテストと検証の黄金時代」。
- pstack の statechart スキル: ユーザー視点の状態機械を可視化し、動画・スクショと並べてレビューしやすくする。

## 成果（Grok Bot チーム、先月）
- 本番へ 11,000 PR を出荷。安定版リリースはほぼ毎日。
- 10月は約227人が1本以上のPRを投稿（カジュアルな drive-by も多い）。
- リバート率は約0.5%で安定（相対的には低下）。
- Electron アプリでありながら、起動・タイピング・チャット開閉などの性能はローンチ時より複数指標で改善。

## 工場の前に
- ソフトウェアファクトリーや全自動化の前に: (1) エージェントの修正はまずコードベースの改善で（アンチパターンの新規混入を lint で防ぎ、既存分も掃除）、(2) 検証の物語を強くする。これらは自動化の前提でもある。
- 土台（コードベース、静的解析、ランタイム＋形式検証）ができれば、その上に工場を建てられる。例: リリースのたびに Grok Bot が Cursor プロジェクトを起動し、アプリ全体を実ユーザーのようにファジングしてバグを見つけ、修正PRを出して自動マージする。大半のプロダクトコードに深い人間レビューはもう要らない。
