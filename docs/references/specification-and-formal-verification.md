# 仕様をつくる人の役割と形式検証

## ガーデンについて共有された考え

ソフトウェアの原点は、人の「こうあってほしい」という欲求にある。何を作り、どの状態を正しいとするかを仕様にすることに、人間が最も労力をかける。その仕様に沿った実装と検証をAIに委ね、ガーデンが仕様を満たした根拠とともに完成を知らせる。最後に完成を判断するのは人間である。

仕様の核として人が定めた不変条件を確かめる手段に、形式検証を取り入れたい。以下は、この考えの背景として共有されたご本人のX投稿。

## X投稿本文

AIがコードを量産する時代になり、長らく学術や宇宙・金融など一部領域の専門家だけのものだった「形式検証（Lean / TLA+ / Quint）」が一気に表舞台へ出てきている。

理由はシンプル。 開発のボトルネックが「コードを書くこと」から「AIが書いた大量のコードをどう正しいと保証するか」に完全に移ったからだ。

■ 「自作自演のオールグリーン」問題

AIに実装を書かせ、同じAIにユニットテストも書かせると、CIは気持ちよくすべて通る。 だがAIが仕様を勘違いしていたり、エッジケースを見落としていたりすると、テストも同じ勘違いを前提に書かれるためバグが素通りする。

かといって、人間がAIの生成した数千行のPRを1行ずつ目で追ってレビューするのはすでに限界。 必要なのは「人間の目視」や「確率的なAIレビュー」ではなく、決定論的に正しさを担保する仕組み（ハーネス）だ。

■ 注目される2つのアプローチ

1, TLA+ / Quint（モデル検査）

分散システムや並行処理、複雑な状態遷移の設計検証に強い。「ユーザー3人、在庫2個、通信遅延あり」といったモデルを定義すると、あり得る全状態遷移を探索し、デッドロックや不変条件違反を洗い出す。ユニットテストでは再現不能な「最悪のタイミングのバグ」を設計段階で潰せる。

2\. Lean 4（定理証明）

型システムを極限まで強化した言語兼証明支援系。TypeScriptが「値の型」、Rustが「メモリ安全」を保証するように、Leanは「配列の範囲外アクセスが起きない」「拒否ルールがあるなら必ず拒否される」といった仕様そのものを型（依存型）で縛り、0〜無限大のあらゆる入力パターンに対してバグが存在しないことを数学的に確定させる。

■ なぜ「今」現実的になったのか

これまで普及しなかった最大の理由は「証明を書くコストが高すぎたから」。 しかし今は、その「証明の泥臭いパズルを解く作業」自体をLLMに任せられる。

AIはハルシネーションを起こすが、LeanやTLA+の検証器は100%決定論的に動く。AIがデタラメな証明を出してもコンパイラが即座に弾き、通るまで自律的にリトライさせられる。「AIの確率的な生成力」と「形式検証の決定論的なチェック」は驚くほど相性が良い。

■ ただし、最大の落とし穴がある

「証明は安くなったが、仕様は安くなっていない」という点だ。

実装も証明もAIに書かせられるようになったが、「そもそも何を正しい仕様とするか」の定義だけは人間の領域に残っている。曖昧な要件を投げて仕様（定理）までAIに書かせると、「間違った仕様に対して100%数学的に正しい証明がついたバグコード」が出来上がる。

これからのエンジニアの主戦場は、実装の細部ではない。 システムの核となる不変条件（絶対に守るべきルール）を見極め、形式的な仕様として定義することへシフトしていく。
