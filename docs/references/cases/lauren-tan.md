# Lauren Tan のソフトウェアファクトリー（ミシュランの厨房）の作り方

## 概要

Lauren Tan（@poteto）は「ソフトウェアファクトリー」という言葉を好まず、Matt Pocock との対談では、エージェントと協働する開発環境を「ミシュランの厨房」にたとえています。工場の比喩は、同じものを効率よく大量に作るイメージです。厨房の比喩では、品質と作り手の技術を保ちながら提供数を増やします。シェフにあたるエンジニアは、環境の設計、道具、手順、品質基準を整え、最終的な品質に責任を持ちます。 [対談の該当箇所](https://www.youtube.com/watch?v=MN9dGgmLyso&t=840s)

> hot take: you don’t need a software factory, and i don’t love the term. it’s just marketing

Tan は、良いソフトウェアエンジニアリングを徹底し、効果の高いところにトークンを投じることを勧めています。その中心にあるのは、エージェントが誤った書き方をしにくい環境づくりです。 [Tan の投稿](https://x.com/poteto/status/2118613050462728659) · [講演の日本語訳](../sources/all-code-is-slop/transcript-ja.md)

講演の原文・訳文・要約を参照できます。[講演資料一覧](../sources/all-code-is-slop/README.md)

## 基本哲学

1. **基盤が先（Foundations First）。** コードベースの品質を上げてから、自動化の範囲やエージェントの数を増やします。基盤が整う前に並列化すると、低品質な変更も増えます。
2. **コードベースは最高の記憶。** 既存のコードはエージェントにとって大きな入力源です。良いパターンが見本になるようにし、複製されたくないパターンは取り除きます。
3. **修正は決定論的なチェックに変換する。** エージェントのミスを直したときは、再発防止をアーキテクチャ、型、lint ルール、CI のチェックなどに落とし込みます。同じ修正を繰り返す手間を減らし、結果を再現しやすくします。
4. **トークンは検証を優先する。** 動作確認、スクリーンショット、実行時検証、形式検証などに割きます。Tan 自身はトークン使用の大半を検証に充てていると述べています。 [講演の日本語訳](../sources/all-code-is-slop/transcript-ja.md)

## 投資の優先順位（Poteto Pyramid）

講演の逆ピラミッドをもとに、土台から人間のレビューまでの優先順位を整理した表です。 [講演の日本語訳](../sources/all-code-is-slop/transcript-ja.md)

| 層 | 内容 | 性質 | 優先度 |
| --- | --- | --- | --- |
| 土台 | アーキテクチャ、API 設計、ディレクトリ構造、型システム | 誤った書き方を構造で防ぐ | 最高 |
| 下層 | lint ルール、コンパイラ、静的解析、テスト | 違反を機械的に検出する | 高 |
| 中層 | Chrome DevTools などによる実行時検証、TLA+ や Lean による形式検証 | 実際の動作や守りたい性質を確かめる | 中 |
| 上層 | `AGENTS.md`、rules、skills、コメント | 判断のよりどころを文章で伝える | 低 |
| 最上層 | 人間のレビュー | 必要な場面で最終判断を行う | 最小限 |

Tan のチームでは、レビューの中心が動画、スクリーンショット、形式検証の結果といった証拠の確認に移りました。 [講演の日本語訳](../sources/all-code-is-slop/transcript-ja.md)

## 具体的な作り方

### 1. コードベースをエージェント向けに整える

誤用を見つけたら、まずアーキテクチャや API を変えて、その書き方を防げるか考えます。構造で防ぎきれない場合は lint を追加し、エラーメッセージで根本原因と直し方を伝えます。Grok Bot では、コメントが回避策の正当化に使われた経験から、大半のコメントを禁止しました。 [講演の日本語訳](../sources/all-code-is-slop/transcript-ja.md)

### 2. 誤用されやすい API を制限する

Grok Bot チームの Dune では、React の `useEffect` をプロダクトコードで禁止し、フレームワーク内部の限られた箇所だけに許可しました。Electron の `main` と `renderer` の相互インポートも、ディレクトリ構造、依存関係の解析、lint で禁止しています。 [講演の日本語訳](../sources/all-code-is-slop/transcript-ja.md)

Cursor では、`setTimeout` などのタイマーがアーキテクチャの衝突を回避する応急処置として広がり、動作の遅延につながりました。こうしたパターンをチェックで見つけ、原因となる設計を直すという教訓です。 [講演の日本語訳](../sources/all-code-is-slop/transcript-ja.md)

### 3. 検証基盤を作る

ユーザー視点で機能をまとめた機能マップ（Feature Map）を用意し、エージェントが再利用できる CLI や Chrome DevTools Protocol でアプリを動かせるようにします。検証結果としてスクリーンショット、動画、トレース、形式検証の結果を残します。UI のプロパティベーステストやファジングも、動作を確かめる手段です。 [開発から本番運用までの検証](../sources/all-code-is-slop/verification-lifecycle.md)

### 4. 修正を資産化する

pstack の `/correct` などを使って、エージェントが繰り返したミスを見つけ、決定論的なチェックに変えます。過去のミスを再現し、新しいチェックで検出できることを確かめます。リポジトリに残したルールや制約は、その後に作業するエージェントにも適用されます。 [pstack の `/correct`](https://github.com/cursor/plugins/blob/main/pstack/skills/correct/SKILL.md)

### 5. 検証基盤を整えたあとの自動化

Tan は、コードベースの設計、静的解析、動作の検証を整えてから、エージェントを起動する仕組みへ自動化を広げる順序を勧めています。検証基盤が整った Grok Bot チームの事例では、リリースをきっかけに Cursor プロジェクトを起動し、ビルドのファジングで見つかった不具合ごとに修正 PR を作成して自動マージします。 [講演の日本語訳](../sources/all-code-is-slop/transcript-ja.md)

## 使用ツール

- **pstack** は Tan が公開した開発スキル集です。`/correct` は再発防止の実装を支援し、`/poteto-mode` は簡潔なやり取り、シンプルなコード、動作を確かめる進め方を示します。 [pstack の `/poteto-mode`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md)
- **Dune** は Grok Bot チームが Electron アプリ向けに作ったフレームワークです。設計上の制約や lint をフレームワークに組み込んでいます。 [講演の日本語訳](../sources/all-code-is-slop/transcript-ja.md)
- **Grok Bot / Cursor Cloud Agents** は、検証基盤の上で並列実行や定型作業を担います。 [講演の日本語訳](../sources/all-code-is-slop/transcript-ja.md)

## 講演で報告した結果

Tan によると、講演の前月に Grok Bot チームは **11,000 件の PR** を本番に出荷し、リバート率は **約 0.5%** でした。Tan 自身も同月に **3,000 件の PR** を本番に出荷し、就寝中の稼働も含めて数千件を出荷できるようになるまで約半年かかったと述べています。品質を維持しながら出荷量を増やした事例としての報告です。 [講演動画](https://www.youtube.com/watch?v=O_zcc6Xl12g)

## 運用時の注意

検証にトークンを多く割くため、短期的には同じ規模の変更でもトークン消費量が増える場合があります。

## 基盤整備を支援するプラットフォーム

複数チーム・複数リポジトリで同じ品質基準を保つ場合は、各リポジトリに制約と検証を組み込む作業を共通基盤で支援できます。再利用できる lint ルール群、アーキテクチャ制約の実装例、検証ツール、機能マップのひな型があれば、担当者ごとの判断に頼っていた手順を他のチームでも再現しやすくなります。Tan による pstack の公開は、開発や検証の手順を他の人が使える形で提供した例です。 [pstack の公開リポジトリ](https://github.com/cursor/plugins/tree/main/pstack)

導入時は、既存のアンチパターンを整理し、違反を検出する決定論的なチェックを各リポジトリで実行できるようにします。共有メモで uehaj 氏の当初案として挙がった「Forge 監視＋イベントハンドラ」は、イベントを検知して処理を割り振る仕組みです。各リポジトリの制約と検証が機能することを確かめてから、こうした起動の自動化や並列実行を広げます。

「ファクトリー基盤」という呼び名は量産を連想させやすいため、基盤の価値は、導入できる制約、再現できる検証手順、確認できる結果を具体的に示して伝えます。

Garden は pstack を共通の開発手順に使い、登録済みチェックの実行方法と結果の形式をそろえます。各プロジェクトは、製品固有の制約、起動・操作手順、検証の実装を自分のリポジトリに持ちます。 [Home Repo の設計と使い方](../../implementation/README.md)

トリガーで仕事を始める自動化の設計例は、Pocock の資料でも参照できます。 [Matt Pocock のソフトウェアファクトリー](matt-pocock-software-factory.md)
