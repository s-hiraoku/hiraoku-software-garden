# 開発から本番運用までの検証

Lauren Tan の講演で示された図をもとに、Cindy Sridharan が紹介した検証手法を、使う段階と目的で整理します。図は本番前の確認に加え、デプロイ、リリース、本番運用中の確認を挙げています。[講演](https://ai.engineer/talks/O_zcc6Xl12g-all-code-is-slop-except-mine) · [Cindy Sridharan の投稿](https://x.com/copyconstruct/status/2118539184654938154)

| 段階 | 確認したいこと | 図にある手法の例 |
| --- | --- | --- |
| 本番前 | 実装が期待する挙動や設計上の制約を満たすか | 単体・機能・契約・回帰テスト、型検査などの静的解析、プロパティベーステスト、形式検証、性能テスト |
| デプロイ | 実際の構成で起動し、依存先や負荷に対応できるか | 統合テスト、設定テスト、負荷テスト、長時間負荷テスト、実トラフィックのコピーを使った確認 |
| リリース | 利用範囲を広げながら異常を検出できるか | カナリアリリース、トラフィックの振り分け、機能フラグ、監視、例外追跡 |
| リリース後 | 実際の利用で起きた問題を発見し、原因を追えるか | ログ・イベント、プロファイリング、トレーシング、実ユーザー監視、監査、当番対応で得た知見 |

デプロイは新しいバージョンを環境へ配置する段階です。リリースは利用者に新しい挙動を公開する段階です。たとえば、サーバーに配置した後で機能フラグを切り替える場合、二つの段階を個別に確認できます。

## Garden での使い方

pstack で共有するのは、守りたい挙動を決め、検証手順を作り、証拠を残す進め方です。各プロジェクトは利用形態と失敗時の影響を見て、必要な段階と手法を選びます。

- **Web サービス**では、PR で主要な操作をテストし、デプロイ時に依存先との接続を確かめます。段階公開を行う場合は、公開範囲を広げる判断にエラー率などを使えます。
- **配布型 CLI** では、代表的な入力で出力と終了コードを検証し、公開前に配布物からインストールして動作を確かめます。利用者から不具合の報告があれば、再現例を回帰テストにできます。
