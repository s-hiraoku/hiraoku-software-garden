# All Code Is Slop (Except Mine) — 日本語訳

Lauren Tan の講演の日本語訳。2026-11-21 に提供された本文を収録しています。[講演資料一覧](README.md) · [動画](https://www.youtube.com/watch?v=O_zcc6Xl12g)

---

はい、皆様こんにちは。改めて自己紹介をすると、私は「Potato（ポテト）」と申します。SpaceX SIで「Grokbot（グロックボット）」の開発に携わっています。

ちょっと挙手をお願いしたいのですが、他の人が書いたコードを見て「これはひどい（スロップだ）」と思ったことがある方はどのくらいいますか？

ええ、私もそうです。

ですが今日は、その「スロップ（粗悪なコード）」を「黄金」に変える方法をお伝えして、皆さんを納得させたいと思います。

先月、私はちょっとクレイジーなことをしまして、本番環境に3,000件のプルリクエスト（PR）を出荷（シップ）しました。エージェントが登場する以前は、一部の例外的な人々を除いて、私たちはコードの「量」をそれほど気にしていませんでした。以前の職場で、私たちはそうした人々を「コーディング・マシン（コード生成機）」と呼んでいました。例えば、かつてGoogleマップのすべてを週末だけで書き直したことで有名なブレット・テイラーのような、信じられないほど生産性の高いエンジニアたちのことです。

しかし現在では、エージェントを使うことで誰もが「コーディング・マシン」になれます。そして私の持論は、これからのソフトウェアエンジニアの仕事、つまりエンジニアであることの本質（メタ）とは、「生産性を劇的に向上させながら、コードの品質をいかにして維持し、さらには向上させるかを見極めること」だということです。

そこに到達するための仕組みを「ソフトウェア・ファクトリー（ソフトウェア工場）」と呼ぶ人もいますが、私はもっとシンプルに考えていて、要は「信頼（トラスト）」がすべてだと思っています。盲目的な信頼ではなく、エージェントが正しいことをやってくれると信頼できるように、エージェントの「環境」に投資することです。

そこにたどり着くにはかなりの労力がかかります。私自身、寝ている間も含めて何千ものプルリクエストを出荷できるようになるまで6ヶ月かかりました。しかし、これは確実に実現可能ですし、皆さんなら私よりもずっと短い時間で到達できるはずです。

ではまず、どのようにして「低信頼」の状態から「高信頼」の状態へと移行するかについてお話ししましょう。

この逆ピラミッドの図は、エージェントの環境にどこまで時間を割くべきかについての私の考え方を表しています。

最初の2つの層は「決定論的（デターミニスティック）」なものです。つまり、コードそのものを利用します。例えば、優れたAPI設計、アーキテクチャ、リファクタリング、あるいはLintルール、型システム、コンパイラ、そして様々な種類のテストなどです。これら2つの層を組み合わせることで、エージェントができることを制限し、デフォルトで正しい行動をとるように強制することができます。

その次の「検証（ベリフィケーション）」は、ランタイム検証と形式検証（フォーマル・ベリフィケーション）の両方を含み、バグを見つけたり、システム内で常に真であってほしい性質や不変条件（インバリアント）をチェックしたりするための優れたツールです。また、エージェントがこちらの目標や意図を正しく理解しているかどうかを確認するのにも役立ちます。

そして最後に、その上に少量の「自然言語（プローズ）」を重ねます。ルールやスキル、`agents.md` のようなファイルなど、人間の判断を必要とする部分です。

まずは「コードベース」から始めましょう。エージェントは入力（インプット）に基づいて出力を生成します。そのため、入力の質が非常に重要になるのですが、たまたま「あなたのコードベースそのもの」が最大の入力源の一つになっているのです。

ですから、エージェントの挙動を修正するときはいつでも、ルールや `agents.md` に新しい行を書き足すのではなく、それを「決定論的なチェック」にできないかと考えてみてください。コードに落とし込む方がはるかに再現性が高く、より強く信頼できるようになります。

私がよく使う例えは、「コードベースは庭のようなものだ」ということです。かつてコードは、一度に数件のプルリクエストというペースでやってきました。2024年に出社して、同僚が書いた3件のプルリクエストをレビューしていたのを覚えています。しかし今日では、その数は300件に近くなっています。

つまり、今やエンジニア一人ひとりが何百、何千ものエージェントからなるチームを抱えているようなもので、コードがあまりにも急速に流入してくるため、まるで途切れない水流のようであり、ほとんど有機的で生き物のようにさえ感じられます。

この例えで言うと、あなたのコードベース、課した制約、設けたガードレールは、まさにこの写真にある建物のように、エージェントが書く新しいコードがその周りに成長していくための「コンクリートの土台」なのです。

そういう意味で、ソフトウェアエンジニアの仕事は「ガーデニング（庭仕事）」に似てきています。コードがエージェントにとって最大の入力であるため、コードベース内にある回避策（ワークアラウンド）、アンチパターン、非推奨のコード、技術的負債はすべて、それが確立されたパターンであるかのように見え、次のエージェントによってそのままコピーされる可能性が高くなります。気づかないうちに庭に雑草や害虫が蔓延してしまうようなものです。

ですから、エージェントが常に「良いもの」だけをコピーするように、コードベースを可能な限り清潔で美しい状態に保つ必要があります。

では、いくつか具体例を見てみましょう。

「Dune（デューン）」は、この有機的なアーキテクチャのアイデアを実装するために私たちがGrokbot向けに作成したクライアントフレームワークです。技術的にはそれほど目新しいものではなく、言わば「Electronアプリ版のNext.js」のようなものだと思ってください。しかしDuneの面白いところは、デスクトップアプリケーションの構築から学んだ多くの教訓を、制約やLintルールとして組み込んでいる点です。

その教訓の一つが、「うまく使うために微妙なニュアンス（加減）を必要とするものは、たいていスロップ（粗悪なコード）につながる」ということです。

古典的な例がReactの `useEffect` です。もちろん適切なユースケースはありますが、非常によく誤用されます。「`useEffect` を使いこなすには博士号（PhD）が必要だ」と冗談を言う人もいるくらいです。言い換えれば、正しく使うには高度なニュアンスの理解が必要であり、エージェントはそれを使うのが得意ではありません。

そこで私たちの解決策は、プロダクトコード内での `useEffect` の使用を単に「禁止」し、DuneのAPI内部の限られた場所でしか使えないようにすることでした。これにより、この問題は事実上完全に排除され、コードレビューで二度とチェックする必要がなくなりました。

私たちが使っているもう一つの興味深いパターンは、「ディレクトリ構造によるコンテキストの付与」です。

Electronアプリである「Cursor」で見られたアンチパターンの一つに、エージェントがメインスレッドのコードをレンダラースレッドにインポートしてしまい、重い処理（ロングタスク）や画面のカクつき（ジャンク）を引き起こすという問題がありました。

そこでGrokbotやDuneのアプリでは、これを非常に厳格な規約にしました。トップレベルに文字通り `electron-renderer` と `electron-main` という2つのディレクトリを用意し、それらの間でのインポートを依存関係グラフ解析ツールとLintルールによって禁止しています。これも設定自体はシンプルなLintルールですが、コードレビューで気にしたり考えたりすべきことが一つ減るという意味があります。

そして、私が見てきた中でもう一つ驚くべきことは、エージェントによる「Markdown（マークダウン）」の使い方です。ドキュメント、コード内のコメント、ルール、スキルといった場所に、エージェントは「なぜ自分が正しいことをしなかったのか」という言い訳（正当化）を書き込むのです。あるいは、皆さんはこんな経験はないでしょうか？こちらがちょっとした修正指示を出しただけなのに、エージェントがそれに過剰反応して、まるで「二度と破ってはならない絶対のルール」であるかのように扱ってしまうことです。

これもCursorでの別の例ですが、エージェントは `setTimeout`、`requestAnimationFrame`、`requestIdleCallback` といった命令型のタイマーを好んで使っていました。VS Codeの命令型スタイルとReactの宣言型スタイルの間にあるアーキテクチャの衝突を、手っ取り早くパッチ当てして誤魔化すために使っていたのです。つまり、私たちのアーキテクチャの選択が、クライアントのパフォーマンスとエージェントのパフォーマンスの両方を大幅に悪化させていました。

JavaScriptでパフォーマンス改善をしたことがある方ならご存知でしょうが、大量のタイマーが急速に生成・破棄されると、大規模なガーベジコレクションが発生し、ひどい遅延やカクつきを引き起こします。

しかし最悪だったのは、スライドの赤字部分のように、エージェントが「なぜこの応急処置が正当化されるのか」を説明する大量のコードコメントを書き残したことでした。気づいたときにはタイマーが至る所に拡散し、アプリのパフォーマンスは大きく損なわれていました。

Grokbotではその教訓を活かし、「コメントの99%を禁止する」という決断を下しました。コメントはすぐに古くなりますし、そもそも人間はコメントを熱心に読んだりしません。それに繰り返しますが、コメントはエージェントに「難しいから正しいことをしなくていい」と正当化するための逃げ道を与えてしまいます。

そしてコメントの最も悪い点は、「強制力がない」ことです。善意で「次のエージェントにこれをやらないように伝えておこう」と書いたところで、結局は全く信頼できるものにはなりません。

そのため、GrokbotとDuneでは現在、エージェントに対して「問題をパッチ当てして回避するのではなく、根本原因（本当の問題）を修正せよ」と指示する、的確で非常に分かりやすいエラーメッセージを出すLintルールを導入しています。

私たちの基本原則は、「エージェントを修正するたびに、それをこうした決定論的なチェックに変えるか、あるいはより良いAPI設計やアーキテクチャによってコード上でその問題を根本から排除できないか考えること」です。

これを十分な回数繰り返すと、コードレビューで注意すべき点がどんどん減っていきます。そしてある時点で、レビューすべきものが何も残っていないことに気づき、エージェントにほとんどのプルリクエストを自分自身でマージさせられるようになるのです。

さて、次に「検証（ベリフィケーション）」も、エージェントの自律性を高め、彼らの仕事に対する私たちの自信と信頼を深める上で非常に重要な要素です。現在、私たちのコードレビューのプロセスは、コードそのものではなく、動画、スクリーンショット、ダイアグラム、形式検証といった「検証の成果物（アーティファクト）」を確認する作業へと縮小しました。

この最も基本的な例が「ランタイム検証」です。これは要するに、エージェント自身がコードを実行し、Chrome DevToolsプロトコルのような人間の開発者も使うデバッグツールを利用できる環境を与える、ということを少し格好良く言ったものです。

私たちのランタイム検証スキルには、「フィーチャーマップ（機能マップ）」と呼んでいるものがあります。これは基本的に、ユーザーの視点から見たアプリケーション内の全機能のサイトマップのようなものです。これがあることで、私たちが「左のサイドバーにあるアレ」と言ったときにエージェントが推測する必要がなくなり、共通の語彙（ボキャブラリー）を持つことができます。また、これらのスキル内ではカスタムCLIも活用しており、エージェントが毎回同じCLIとドライバーを再利用できるようにすることで、トークン消費量を削減し、テスト可能性も高めています。

さらに最近では、「形式検証（フォーマル・ベリフィケーション）」にも取り組み始めています。現在、複数のデバイスやプラットフォームにまたがる通知機能などの主要なユーザーフローのモデル検査を行うために「TLA+」を使用しています。また、特定のアルゴリズムを証明するために「Lean」も使っています。例えば、私たちは独自の仮想化（バーチャライゼーション）ライブラリを書いたのですが、画面のちらつきやガタつき（ジッター）が起きないことをチェックするためにLeanを使っています。

全体としてこのアプローチはまだ実験段階ですが、非常に有望だと感じています。すでに形式検証によってかなりの数のバグを発見しました。もちろん銀の弾丸（万能薬）ではありませんが、エージェントの環境におけるもう一つのツール、もう一つの層として位置づけています。

また、動画がとても速くて見づらいかもしれませんが、UIに対する「プロパティベーステスト」も始めたばかりです。私たちは「Bombadil」というライブラリを使用しており、これもすでにいくつかのUIバグを検出してくれています。

ここで少し視点を引いてみましょう。シンディ（Cindy）という方のツイートを見かけたのですが、6ヶ月前、彼女は「微妙なバグがマージされてしまうため、エージェントを信頼できない」と話していました。彼女がエージェントを信頼するために本当に欠けていたのは「検証プロセス」でした。そして6ヶ月後の今、彼女は「1日のトークンの70%を検証に費やしている」と語っています。これは私自身の感覚とも一致しており、私のトークン使用量の大半も検証に使われています。

彼女のプロセスをよく見てみると、そこにある手法はどれも目新しいものではなく、私たちがこれまで持っていなかったような新技術でもありません。どれも単なる「優れたソフトウェア工学のツール」ですが、以前は理解したり、書いたり、維持したりするのが難しかったため、コストが高すぎて手が出せなかったものばかりです。しかし、エージェントがそのコストを劇的に下げてくれました。

私たちは今、まさに「ソフトウェアテストと検証の黄金時代」に突入しています。エージェントのおかげで、以前は経済的に見合わなかったレベルまで、あらゆるものを徹底的にテストできるようになったからです。

さらに形式検証は、プロダクトがどのように機能すべきか、そしてエージェントがこちらの意図や目標を本当に理解しているかをより深く考察する助けにもなります。私は自分のプラグイン「P-stack（Potato Stack）」の中に、「ステートチャート（状態遷移図）」という新しいスキルを作りました。これはユーザーの視点から見たステートマシンを視覚化するもので、私たちが用意する動画やスクリーンショットと並べてレビューすると非常に確認しやすいです。これはとても重宝しています。

（※スライドの切り替わりに対して）フラッシュバックしてしまってすみません。

さて、ではその「約束の地」はどのような景色なのでしょうか？こうした投資のすべてに対して、どんな見返りが得られるのでしょうか？

Grokbotチームでは開発スピード（ベロシティ）が急上昇しており、先月はなんと「11,000件」ものプルリクエストを本番環境に出荷しました。途方もない数字です。クライアントのリリース頻度も上がっており、およそ1日に1回のペースで新しい安定版（ステーブル版）を切り出しています。

コアチームも以前よりはるかに多くのコードを出荷していますが、コンテキストを十分に持っていないカジュアルなコントリビューターや、通りすがりの貢献者もたくさん参加しています。10月には約227人が少なくとも1件以上のプルリクエストを貢献してくれました。

これほど開発スピードが加速していると、「現場は大混乱になるのでは？スロップだらけになるのでは？」と思うかもしれません。しかし実際には、リバート（取り消し）されるPRの割合は相対的に低下しており、約0.5%という低い水準で安定しています。

そして、この出荷ペースとPRの量において本当に興味深いのは、Grokbotのパフォーマンスがリリース当初と比べて「安定している」どころか、複数の側面で「向上している」という点です。起動速度、タイピングの反応、新しいチャットの開始、チャットの切り替えなど、これらすべてが高速化しています。

しかも忘れないでいただきたいのは、Grokbotは今のところまだ「Electronアプリ」だということです。ですから技術的な上限（天井）はあるわけですが、それでも世の中の他の多くのエージェントUIよりもすでにずっと高速です。これだけの開発スピードとこれだけ多くのコントリビューターを抱えるElectronアプリとしては、かなり優秀だと言えるのではないでしょうか。

ですから、皆さんがソフトウェア・ファクトリーの構築やあらゆることの自動化に飛びつく前に、まずはエージェントを修正するたびに「コードベースを改善すること」から始めてみてください。新しいアンチパターンの発生を防ぐためにLintルールを作ることから始め、その後で古いパターンも一掃します。そして、検証の仕組みを本当に強固なものにしてください。

こうした作業の多くは、そもそも自動化のための前提条件です。もし内側のコーディング・ループがスロップ（粗悪品）を生み出しているなら、そのループを自動化しても「より多くのスロップ」が生み出されるだけで、問題を解決するためにどんどん多くのトークンを投入する羽目になります。そしてご存知の通り、トークンは非常に高価です。

コードベース、静的解析、ランタイム検証や形式検証といった土台に投資をすれば、その基盤の上に多くのことが可能になることに気づき、自分だけのファクトリーをとても簡単に構築できるようになります。

そして準備が整ったら、Grokbotはその外側のループを構築するのに最適なツールです。Cursorやクラウドエージェント、プロジェクトを起動できる多数のコネクタやルーチンを備えており、何百、何千ものエージェントをオーケストレーション（統合制御）することができます。

手短な例を挙げると、現在私たちが新しいリリースを切り出すたびに、Grokbotが自動的に新しいCursorプロジェクトを立ち上げ、アプリケーション全体、ビルド全体に対してファジングテスト（予期せぬ入力を大量に与えてバグを探すテスト）を実行します。実際のユーザーのようにアプリを動かしてバグを見つけ出し、見つかったバグの一つひとつに対して修正用のPRを作成し、信じられないかもしれませんが、それを「自動マージ（オートマージ）」するのです。

なぜそんなことができるのかといえば、私たちのコードベースが十分に整っているため、作成されるプルリクエストがデフォルトで高品質なものになりやすく、私たちがマージするほとんどのプロダクトコードにおいて、もはや人間による深いレビューが不要になっているからです。

つまり、しっかりとした土台と優れた有機的なアーキテクチャがあれば、スロップを黄金に変えることができ、品質を一切妥協することなく、高い開発スピードでプロダクトを出荷することができるのです。

私の名前はPotato、本名はLauren（ローレン）です。ご清聴いただき、本当にありがとうございました。
