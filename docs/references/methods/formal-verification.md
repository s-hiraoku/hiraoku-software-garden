# 形式検証の入口

| 手法 | 向いている問い | 確認できる範囲 |
| --- | --- | --- |
| **TLA⁺とTLC** | イベントの順序や並行実行が変わっても、不変条件が守られるか。行き詰まる状態はあるか。 | 定義した初期状態・遷移・定数からなる有限モデルについて、探索が完了すれば到達可能な状態を確認できる。[TLA⁺公式ツールのTLC解説](https://github.com/tlaplus/tlaplus/blob/bc1b506bdcad80bb518bf3776a9161c34ff0fc4c/USE.md#model-checking-with-tlc) |
| **Quint** | 状態遷移の仕様を試し、どういう順序で不変条件が破れるかを追えるか。 | 公式の銀行口座例では、シミュレーションが残高の不変条件を破る実行を検出し、再現用のシードを返す。モデルの状態遷移は、Apalacheによる記号的モデル検査でも調べられる。[Quint公式の銀行口座例とツール解説](https://github.com/quint-co/quint/blob/20959113bdb6275da970902974e38821f9ebdd42/quint/README.md) |
| **Lean 4** | 関数・データ構造・アルゴリズムが、定義した前提のもとで常にある性質を満たすと示せるか。 | 定式化した命題に対して検査済みの証明が得られる。証拠の範囲は、命題が参照する定義と使った仮定で決まる。[Theorem Proving in Lean 4の命題と証明](https://github.com/leanprover/theorem_proving_in_lean4/blob/14ce16a2b76b34585221c51c1eeefbfe36e0ce58/book/TPiL/PropositionsAndProofs.lean) |

例えば、同じ仕事の完了通知が二重に届いても確定処理は一度だけ、という性質なら、モデルに通知の重複や順序の違いを含められます。検査で反例が出れば、どの遷移で不変条件を破ったかを追えます。実際のアプリケーションについては、テストや実行時の観測を通じて、モデルで表したように動くかを確かめます。

検証結果を読むときは、「何を正しいとするか」「どの前提を置いたか」「どの範囲を調べたか」「完了したか」が分かると判断しやすくなります。人が不変条件を定める理由と、実装とテストが同じ思い違いをする問題は、リポジトリの共有資料にあります。[仕様をつくる人の役割と形式検証](../specification-and-formal-verification.md)
