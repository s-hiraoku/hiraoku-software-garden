# 実装への適用方針（案）

状態: 未実装・未確定。プロジェクト README のフェーズと講演資料から整理した検討案です。

## Phase 1: 環境と検証の土台

対象となるコードや技術スタックが確定した段階で、次の順に整えます。

| 検討対象 | 実装する仕組み | 完了を判断する証拠 |
| --- | --- | --- |
| 守るべき設計・境界 | ディレクトリ構造、API、依存関係の制約 | 許可される例が通り、違反例が失敗する |
| 決定的なチェック | 対象に合う lint、型検査、テストと統一実行コマンド | ローカルと CI で同じチェックが動く |
| ユーザーから見た挙動 | 機能マップ、再現手順、ランタイム検証 | 期待する挙動と結果を照合できる |
| 失敗の切り分け | 環境不備と実装不具合を区別する診断 | エージェントが次の調査先を特定できる |

現時点でアプリケーションコードはなく、使用言語やフレームワークも未選定です。具体的なツールや禁止ルールは対象が決まってから選びます。

## Phase 2: 修正をチェックへ変える

不具合やレビュー指摘が発生したら、再現条件と期待する挙動を確認し、型・lint・テスト・API 設計のどこで再発を防ぐかを判断します。単発の指摘を、そのまま全体への禁止事項にしないようにします。

## Phase 3: 外側ループを接続する

内側の実装・検証ループが再現可能になってから、信号の検知、起票、実装、検証、マージ候補の提示を接続します。自動マージの条件は未定です。

## 講演の実例を採用するとき

Dune の `useEffect` 制限、Electron の依存境界、コメント制限、TLA+ や Lean の導入は参考例です。このプロジェクトでの具体的な課題と、制約によって防ぐ不具合が明らかになったときに採否を判断します。
