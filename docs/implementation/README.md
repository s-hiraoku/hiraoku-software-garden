# Home Repo の設計と使い方

hiraoku-software-garden は、独立したプロジェクトに共通の開発手順を提供します。エージェントを Garden から起動し、対象リポジトリを選びます。Web アプリや CLI などの違いに応じて、各リポジトリで設計、実装、検証の具体的な方法を決めます。

## 責務

| 場所 | 管理するもの |
| --- | --- |
| Garden | リポジトリの一覧、共通の開発ハーネスと作業手順、チェックの呼び出しと結果の共通形式 |
| 対象リポジトリ | プロダクトコード、固有の指示や仕様、ハーネスの実装と依存関係 |
| 実行環境 | Git の認証、ローカルのチェックアウト、各リポジトリの実行環境と依存パッケージ |

[Matt Pocock の Home Repo Pattern](https://www.aihero.dev/the-home-repo-pattern) を作業の起点にし、[Lauren Tan の講演](../lauren-tan-all-code-is-slop/README.md) にある決定的なチェックと再現できる検証を各リポジトリで育てます。共通基盤から既存のコマンドを引数の配列で呼び出すので、対象の言語やエージェントの種類が変わっても実行方法をそろえられます。

## 共通の開発ハーネスとプロジェクト固有のハーネス

Garden 配下の全プロジェクトで、開発を進めるための共通ハーネスとして pstack を使います。目的や設計を詰める手順と、検証スキルを作成・保守する手順を共有します。例えば `create-verification-skill` で対象に合う検証スキルを作り、その成果物を対象リポジトリで管理します。アプリの変更に合わせて `maintain-verification-skill` で起動・操作・証拠の取り方を更新します。[pstack の上流リポジトリ](https://github.com/cursor/plugins/tree/main/pstack)

プロジェクト固有のハーネスは、その製品をどう起動し、何を操作し、何をもって成功とするかを持ちます。選んだライブラリやドライバー、テストデータ、再発防止チェックも対象リポジトリに置きます。Garden は登録されたコマンドを呼び出します。

この段階では、共通で使うハーネスの方針とチェックの実行入口を提供します。pstack の配布やバージョン管理、各プロジェクト固有のハーネスの整備は、最初の新規プロジェクトを登録する際の作業です。

## プロジェクトで共通に使う開発手順

1. **目的を決める**。誰の何を改善するか、どの挙動を確認できれば完了かを明らかにする。
2. **小さく実装する**。一度に確認できる変更に分け、対象リポジトリの設計や既存の手順に沿って進める。
3. **動かして確かめる**。自動チェックを通し、変更の目的に対応する実際の挙動を確認する。
4. **レビューに証拠を残す**。確認した条件、手順、結果、未確認の点を共有する。
5. **失敗を次の改善に使う**。再発を防ぐ価値がある失敗は、対象リポジトリの API 設計、型、lint、テストに反映する。複数のプロジェクトで使える知見は Garden の手順やツールへ還元する。

例えば、Web アプリでは画面上の操作と表示を、CLI では入力に対する出力や終了コードを確認します。両方で使うのは「期待を決め、実際に確かめ、結果を残す」という手順です。上記はチームやエージェントが使う作業手順です。現在の CLI が提供するのは、リポジトリの一覧と自動チェックの実行です。

## プロジェクトに合うハーネスを組む

ハーネスは、エージェントが設計上の制約を守り、実装した挙動を自分で確かめられるようにする仕組みです。プロジェクトごとに守りたい性質を決め、それを検証できるライブラリやツールを選びます。既存のライブラリで足りない部分は、対象に合うドライバー、チェック、API を作って補います。

| 対象の例 | 守りたい性質 | ハーネスに組み込むもの |
| --- | --- | --- |
| Web アプリ | 保存した内容が画面を開き直しても表示される | テスト用データ、ブラウザ操作、表示結果の検証 |
| ファイル変換 CLI | 不正な入力を受けたら失敗を伝え、出力ファイルを残さない | 入力例、一時ディレクトリでの実行、終了コードとファイルの検証 |

ライブラリの依存関係、設定、検証コードは対象リポジトリで管理し、そこで実行するチェックコマンドを Garden に登録します。これにより、プロジェクトは自分の用途に合うハーネスを独立して変更でき、Garden からは同じ方法で実行できます。

検証方法を選ぶときは、PR や CI で確認する挙動と、配布・公開後の環境で確かめる挙動を明らかにします。配置、公開、運用に必要な確認はプロジェクトの配布形態に合わせて設計します。[開発から本番運用までの検証](../lauren-tan-all-code-is-slop/verification-lifecycle.md)

講演の Dune は、プロダクトの設計制約を API や lint に組み込んだ例です。自作の一覧描画ライブラリはプロダクトの機能で、そのアルゴリズムの性質を検証する役割を Lean が担います。[Lauren Tan の講演資料](../lauren-tan-all-code-is-slop/README.md)

## 現在使える操作

Python 3.11 以上と Git が必要です。Garden と対象リポジトリを同じ親ディレクトリに置き、対象側の手順に従って依存関係を準備します。

```sh
python3 garden.py list
```

`list` は登録済みのリポジトリを表示します。初期カタログは空で、新規プロジェクトを割り当てるまでは `{}` を返します。登録後は、ID を渡すと `check` が対象の Git 作業ツリーのルートでチェックを順に実行します。

```sh
python3 garden.py check project-a project-b
```

`project-a` と `project-b` は、登録したリポジトリの ID に置き換えます。このコマンドが実施する範囲はカタログの `check` で確認できます。

`check` の標準出力は JSON です。対象、実行コマンド、開始前のコミットと変更の有無、結果を記録します。各コマンドの出力は標準エラーで確認できます。

| 結果 | 意味 |
| --- | --- |
| `passed` | チェックコマンドの終了コードが 0 |
| `failed` | チェックコマンドが非ゼロで終了。原因はコマンドのログを確認する |
| `unavailable` | チェックアウトが見つからない、Git 情報を読めない、コマンドを起動できないなどの理由で実行できなかった |

全件成功で終了コード 0、失敗または実行不可があれば 1、実行対象が未登録の場合や CLI の引数またはカタログに誤りがあれば 2 を返します。結果は各作業ツリーに対するチェックを表します。複数リポジトリをまたぐ挙動は、今後、対象を組み合わせる専用シナリオで検証します。

## リポジトリを追加する

[garden.toml](../../garden.toml) に安定した ID、ローカルのパス、リモートの URL、概要、既存のチェックコマンドを登録します。リモート URL はチェックアウト先を案内する情報です。CLI は登録されたローカルパスを使います。パスは `--workspace` からの相対パス、または絶対パスです。別の登録一覧を使う場合は `--catalog` を指定できます。両オプションはサブコマンドの前に置きます。

```sh
python3 garden.py --workspace "$PWD/../projects" --catalog my-garden.toml check my-repo
```

`check` は信頼できるカタログから、手元の権限で対象コマンドを実行します。各リポジトリで使っているコマンドを登録し、チェックアウトとセットアップは実行前に用意します。

## 実装の進め方

1. **Phase 1**。複数リポジトリの発見とチェック実行を入口に、対象ごとの再現手順、設計の境界を守るチェック、実行環境を整える。ユーザー向け機能の確認には機能マップと動作の証拠を残す。
2. **Phase 2**。実際の不具合やレビュー指摘から、どの型、lint、テスト、API 設計で再発を防げるかを判断する。複数のプロジェクトに共通する手順は Garden に還元する。
3. **Phase 3**。実装と検証を再現できるようになったら、信号の検知から起票、実装、検証、マージ候補の提示へつなぐ。実行先や自動マージの条件は未定。

`useEffect` やコメントの制限、TLA+、Lean は、講演で紹介された実例です。各リポジトリの課題に応じて制約や検証方法を選びます。
