# hiraoku-software-garden

種類の違うソフトウェアを、共通の開発手順で育てるための Home Repo です。pstack を全プロジェクト共通の開発ハーネスとして使い、目的と完了条件を決め、小さく実装し、動作の証拠を残し、失敗から次の変更を改善します。各プロジェクトは、固有の仕様と技術スタックに合うライブラリを選び、設計の制約や動作検証の手順と組み合わせてハーネスを育てます。

Garden から対象のリポジトリを探し、登録されたチェックを同じ入口で実行できます。最初の対象には、新しく割り当てるプロジェクトを登録します。

**Software gardening** は、実際の失敗を手がかりにコードベースと検証の仕組みを育て続ける考え方です。[Home Repo の設計と使い方](docs/implementation/README.md)

## 中心の考え: 信頼は環境で作る

エージェントに大量の変更を任せられるかどうかは、モデルの賢さではなく **環境への投資** で決まる。
文章のルール（AGENTS.md 等）への依存を最小化し、決定的なチェックに寄せる。

### 信頼ピラミッド（下ほど厚く投資する）

1. **コードベース自体** — API 設計、アーキテクチャ、ディレクトリ構造そのものが文脈と制約になる
2. **静的解析** — lint、型、コンパイラ、テスト。「ニュアンスが要るものは禁止してカテゴリごと消す」
3. **検証** — ランタイム検証（エージェント自身が動かして確認する）、形式検証、プロパティベーステスト。レビューはコードではなく検証の成果物（動画・スクショ・図）を見る
4. **文章のルール** — skills や AGENTS.md は一番上に薄く。判断が要るものだけ

## 運用原則

- **修正はチェックに変える**: エージェントを直すとき、AGENTS.md に1行足すのではなく、lint / 型 / テスト / 設計の変更に変換する。再現性のある形で残す
- **コードベースは庭**: コードは連続した流れで届く。アンチパターンは次のエージェントがコピーして広がる（雑草）。pristine に保つ手入れが仕事になる
- **庭師の役割**: 整備の知見はバッファに溜め、数日ごとに環境（skills、制約、lint、型）そのものを直す
- **検証にトークンを使う**: 実績ではトークン使用の大半が検証。生成は安い、検証が本番
- **悪いループを自動化しない**: 内側のループが slop を出すなら、自動化は slop の増産。土台が先、外側の自動化は後

## フェーズ

- **Phase 0**: この repo の立ち上げ（思想と運用の置き場）
- **Phase 1**: 環境と検証の土台 — 決定的チェックの整備と、検証スキル（失敗の切り分けまで含む）の構築
- **Phase 2**: 「修正→チェック化」の運用を回す
- **Phase 3**: 外側ループの配線 — 信号→起票→エージェント実行→検証→マージ候補（3層ループの L0/L1 と接続）

## 3層ループとの関係

- L0 Ambient Outer: Grok Bot / Muse（信号検知）
- L1 Orchestration Outer: Cursor Projects / Claude Projects（文脈保持、仕様化、タスク分解）
- L2 Inner: Claude Code / Cursor Agent（実装）

この repo は、その土台となる「環境と検証」の側を担う。
